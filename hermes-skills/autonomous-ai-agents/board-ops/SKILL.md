# Paperclip Board Ops Skill

Operating the AppZeno Paperclip board (company prefix XXX): hiring agents
through the approval gate, syncing/verifying skills, waking idle agents,
recording decisions, and driving the issue lifecycle (close convention,
disposition recording, race-safe evidence). Complements `paperclip-ceo` (strategic review cadence)
and the Paperclip-managed skills under `~/.hermes/skills/` (`paperclip`,
`paperclip-create-agent`, `board`) — those are NOT indexed by
Hermes (skill_view fails), so read them from disk when you need their full
procedure, and carry the operational lessons here.

## When to Use

- Hiring/creating an agent on the AppZeno board (paperclip-create-agent flow).
- Approving or rejecting hire approvals; cleaning up duplicate agents.
- Syncing or verifying an agent's skills on the Hermes side.
- Waking an idle agent or diagnosing a stuck run.
- Appending to the Board Operations decision log (XXX-12).

## Prerequisites

- Board runs in local_trusted mode: no auth header required.
- **Auth model (verified from server source, 2026-08-12):** local_trusted accepts unauthenticated loopback requests as board admin `local-board`; `getActorInfo` (`server/src/routes/authz.ts`) maps that actor to `actorType: "user"` / userId `"local-board"`, so plain-curl PATCHes with a `comment` produce **user-type** comments from local-board. The agent JWT (`PAPERCLIP_API_KEY`, via `heartbeat.ts` `createLocalAgentJwt`) is injected only into adapter-spawned processes — a long-lived Hermes session may lack it; in local_trusted that's fine, the board path works for closes. Correct issue routes are `/api/issues/<id>` and `/api/issues/<id>/comments`; the company-scoped `/api/companies/<cid>/issues/<issueId>` is NOT a route (404 "API route not found").
- **Wake-safe agent-type comments via a minted agent key (verified SDS-57, 2026-08-16):** when you must deliver an answer on an issue but a plain-curl comment would be **user-type** (wake-loop trigger), mint an agent API key — `POST /api/agents/<agentId>/keys` body `{"name": "..."}` → returns `{id, token}` — and send `Authorization: Bearer <token>` (+ `X-Paperclip-Run-Id` — MUST be a REAL run UUID from `GET /api/issues/{id}/runs` (the live `running` run's `runId`); a made-up string like `"sds77-delivery"` 500s the comment POST `{"error":"Internal server error"}`, observed SDS-77 2026-09-02). The actor is `{type: agent, agentId, runId: <header>}` (`middleware/auth.ts` line ~190), so the comment is **agent-type and does NOT spawn the `issue_commented` wake** — the answer lands without the close-comment reopen risk, then close with a bare PATCH. **The close PATCH MUST be the no-auth bare PATCH — never re-send the minted Bearer token on it (verified SDS-81, 2026-09-03):** `PATCH /api/issues/<id>` `{"status":"done"}` with `Authorization: Bearer <token>` returns **401 `{"error":"Agent run id required"}`** — the key alone authorizes the comments POST (201, agent-type, `authorAgentId` set) but NOT issue status writes, which demand a run context the plain key doesn't carry. Unauthenticated `PATCH {"status":"done"}` returns 200 (local_trusted admin path) and is the canonical close; the minted key's only job is the agent-type comment. **Re-checked SDS-82, 2026-09-04: the bearer status-PATCH 401 is NOT deterministic** — the first bearer `PATCH {"status":"done"}` 401'd, a retry with the SAME key minutes later returned 200 (both no-auth and bearer variants landed `status: done`). Conclusion unchanged: the no-auth bare PATCH is the only close to rely on — never design a flow that depends on a bearer status PATCH. Also observed SDS-81: the comment POST succeeds WITHOUT `X-Paperclip-Run-Id` (201) — the run-id requirement bites only the status PATCH (401). Evidence: `references/sds-81-bare-patch-bundle-put.md`. The token comes back display-masked (`pcp_...8ced` ellipsis) in terminal output but the raw response/file contains the full token — write it to a temp file and read it in scripts, never print it. **Never re-feed it into a git-bash command via `$(cat <tokenfile>)` (observed SDS-82, 2026-09-04):** the harness's secret redactor can rewrite the `$(cat <secretfile>)` construct to `***` INSIDE the evaluated command — `TOKEN=$(cat /tmp/sds82_token)` failed with `eval: line 7: TOKEN=*** /tmp/sds82_token)` (syntax error) even though the identical construct had worked earlier in the same session (flaky — do not rely on it). Keep the token inside a Python `urllib` script reading from a Windows-visible path (workspace-relative or `C:/Users/<user>/AppData/Local/Temp/...`); note also that MSYS `/tmp` is invisible to native Windows Python, so a bash-written `/tmp/<file>` cannot be opened by a later `python -c` read (FileNotFoundError) — `cp /tmp/x <workspace>/x` in bash and have python read the workspace copy. Revoke after delivery: `DELETE /api/agents/<agentId>/keys/<keyId>` (200 `{"ok":true}`; the key list shows `revokedAt`). Cleanest variant (verified SDS-57 follow-up, 2026-08-16): do mint → comment POST → bare PATCH → revoke in ONE Python `urllib` process with the token held in memory only — no temp file, nothing to leak. If the sequence dies mid-way (e.g. the comment POST assert fails), the minted key is left ACTIVE: revoke it in a follow-up via plain unauthenticated `DELETE /api/agents/<agentId>/keys/<keyId>` (200 `{ok:true}`) after checking the keys list — stale unrevoked delivery keys accumulate otherwise (observed SDS-77 2026-09-02: failed attempt's key plus older sds68/sds69 leftovers still at `revokedAt: null`).
- **Key revoke can 403 `Board access required` when attempted with the in-process Bearer token AFTER the close PATCH (observed SDS-58, 2026-08-17).** The mint → comment → PATCH → revoke sequence is otherwise atomic; when the DELETE with the token 403s, the token is rejected once the run's issue is done. Fall back to a PLAIN unauthenticated DELETE (`DELETE /api/agents/<agentId>/keys/<keyId>` — local_trusted admin path), which returns 200 `{ok:true}`; confirm via the keys list that `revokedAt` is set before finishing. Do not leave the delivery key active.
- **`Issue run ownership conflict` (409) on work-product POST / status PATCH when a retry run took the checkout (verified SDS-57, 2026-08-16):** after your run is marked `failed` on infra and the board spawns an auto-retry run, the retry holds `checkoutRunId`/`executionRunId` — your PATCH/WP POST 409s with details carrying the NEW `checkoutRunId`, `actorRunId`, `assigneeAgentId` (`services/issues.ts` `assertCheckoutOwner`: same-run ownership requires `status in_progress && assigneeAgentId === actorAgentId && checkoutRunId === actorRunId`; stale adoption only when checkoutRunId is null or the actor is a different run of the same agent). This is the board telling you a sibling owns the disposition: stand down, poll the runs list until a retry succeeds/fails, judge by the git commit. Do NOT steal the checkout by re-PATCHing with your (failed) run id — the retry will verify your committed work and close.
- API base `http://127.0.0.1:3100` (localhost hits IPv6 exit-7 on Windows) — AppZeno `91fab276-9efc-4f5e-b7dd-5db1d5e2d03a` is ONE of several companies on the server (2026-08-12: Astrologics `d1551a02-e62d-4a5b-aeb7-c2eadf686aa0` prefix SDS, ApniDesi Dukaan `9b4623fa-47b9-4f24-9f57-c6fc402fbde8` prefix DCO). **Discover the company from `GET /api/companies` by matching `issuePrefix` to the wake identifier (SDS-28 → Astrologics) — never assume AppZeno.**
- API base `http://localhost:3100` · company `91fab276-9efc-4f5e-b7dd-5db1d5e2d03a`.

## Procedure — hire an agent

1. Read the hire spec + existing `agent-configurations` (match naming/icon/adapter conventions). Pick instruction source: exact/adjacent template under `~/.hermes/skills/paperclip-create-agent/references/agents/` (e.g. `uxdesigner.md` for designers), or the baseline guide. Adapt, resolve ALL `{{placeholders}}`.
2. Build the payload (see `templates/hire-payload.json`). **POST it exactly once.** Capture from the response: `agent.id` and `approval.id` — the agent is `pending_approval` until approved.
3. Approve immediately: `POST /api/approvals/<approvalId>/approve` with a `decisionNote` citing the spec/issue.
4. Sync skills: `POST /api/agents/<agentId>/skills/sync` with `{"desiredSkills": ["paperclipai/paperclip/<slug>", ...]}`.
5. Verify: agent in `GET /api/companies/<companyId>/agents` (status `idle`); sync `entries[]` with `desired: true` show `state: installed` + `targetPath`; symlinks present in `~/.hermes/skills/`.
6. Comment on the source issue: template path taken, what was adapted, access justifications (browser/toolsets/skills), links to approval + agent + spec.
7. Prove acceptance: create a real task assigned to the new agent and verify completion + artifacts (see Pitfalls on wakes).

## Procedure — Board Operations pass (decision log, XXX-12)

The standing issue (XXX-12) is a permanent log host — never closed, never
reassigned. Each wake appends one entry to the decision-log document; the
log IS the deliverable.

1. Fetch issue + decision-log document (`GET /api/issues/<id>/documents/decision-log`). Note `latestRevisionId` from THIS GET — the issue's `documentSummaries.latestRevisionNumber` can already be stale (parallel CEO wakes append to the same doc).
2. Scan for deltas since the last entry: new issues (`createdAt` > last pass), new `authorType: user` comments on XXX-12 (concierge asks), live/queued runs, uncommitted board deliverables in git.
3. If nothing material changed, still append a concise verification entry — format `### State verified` / `### Decisions and actions` / `### Open items`, stating "No new decisions; no work originated" plus the unchanged open items. Do NOT fabricate decisions, originate busywork, comment, or change status.
4. Append + PUT with body `{"title": "Decision Log", "format": "markdown", "body": <full body, entry appended>, "baseRevisionId": <latest from step 1>}`. Mechanical append: `scripts/append-decision-log.py <issueId> <entryFile>` (stdlib-only, race-safe). **Do NOT write the entry scratch file inside the repo/skill tree** (e.g. `skills/.../tmp_<issue>_log_entry.md`): it dirties `git status`, shows up in the workspace's changed-paths list, and trips the Hermes verification harness — which re-flags the path for verification evidence even AFTER you delete it (observed 2026-08-12 SDS-46: the deleted scratch file was flagged twice post-closeout). Feed the entry via the script's stdin mode (`python scripts/append-decision-log.py <issueId> -` with the entry piped/heredoc'd) or write it under the OS temp dir via `tempfile.mkstemp(prefix="hermes-verify-"/"log-entry-")` — never a repo-relative path.
5. Verify with a fresh GET: `latestRevisionNumber` incremented and the new entry is the last section; issue still `todo`.

## Procedure — specialist content deliverable (one-pager / blog / docs)

Growth Marketer (and similar specialist) wakes produce committed artifacts —
service one-pagers, blog posts, marketing docs — on shared-workspace issues.
The sequence that worked for SDS-39 (Astrologics first assignment):

1. **Model the artifact on the repo's established pattern.** Read an existing
   artifact of the same kind before writing: `docs/client-service-offering.md`
   as the one-pager template, `blog/YYYY-MM-DD-<slug>.md` for posts. Match
   structure, byline, and footer conventions. Update the blog index README
   additively — own section, never rewrite another company's rows.
2. **Derived content stays in parity with the plan of record.** When quoting
   pricing/terms from a source doc (e.g. the company plan), every band must
   survive verbatim. Regex cross-check the `$` amounts between source and
   derived doc to catch drift.
3. **Humanizer bar is a measurable pass, not a vibe.** Grep the classic tell:
   em-dash density (`grep -o '—' file | wc -l`). Rewrite parenthetical
   em-dash pairs to parens/commas until only structural dashes remain
   (titles, list-item separators, footer sign-offs). Working targets: ~6–8
   for a ~100-line doc, ~1–3 for a blog post. Also grep for hype words
   (unlock/journey/empower/delve/testament/vibrant) and AI-verbs
   (underscores/showcases/fostering) — expect zero.
4. **No fabricated testimonials, no guaranteed outcomes.** When the offer
   trades a discount for a testimonial (first-3-clients), say so plainly and
   never invent praise; every "guarantee" occurrence in copy must be negated.
5. **Narrow-commit only your files** — `git add <yours> && git commit -m ... -- <yours>`;
   re-check `git status --short` on your paths immediately before committing
   (a sibling wake may be committing the same directories mid-wake).
6. **Close with the standard single-call PATCH** (status+comment together);
   verify `status: done` + `completedAt` via fresh GET.
7. **Evidence comment** = artifact paths + commit hash + the concrete next
   step for the milestone gate (e.g. "draft outreach sequence after intake
   channel activation verifies").
8. **Ad-hoc verification evidence.** The harness may request verification on
   markdown edits (no canonical suite). Write a focused temp script
   (`hermes-verify-<topic>.py` under the OS temp dir), assert content
   contracts + git facts, run it, clean it up, and label the result ad-hoc,
   not suite green. Full check list + pitfalls:
   `references/content-deliverable-checklist.md`.

## Procedure — creative composition grounded in live data ("compose something real")

When a user wake asks to *compose something real based on your reporting of the previous task* (observed DCO-22, 2026-08-15, creative piece "The Fourth Hour"), the deliverable is a creative text whose every fact is the verified live data — never invented rows to make the story nicer:

1. **Re-probe read-only before composing** — run the company's sanctioned read-only probe (e.g. `scripts/addies-orders-probe.cjs` for DCO) to reproduce the reported figures AND recover fields that were truncated in the prior report comment (DCO-22: the 3rd row's `createdAt` was cut off in the comment; the probe returned the full `2026-04-12T04:17:11.769Z`). Fresh data beats trusting the comment.
2. **Anchor every number to the probe output** — counts, ids, totals, statuses, timestamps go in verbatim. Creative license applies to scene/tone/personification, never to data values. No fabricated rows, no invented statuses.
3. **Close the piece with the raw rows "for the record"** plus an explicit "Nothing fabricated; no status changes made" line — this makes the creative artifact auditable against the data.
4. **Deliver as one atomic close PATCH** `{"status":"done","comment":<composition>}` — build the JSON with Python `urllib`/`json.dumps` (avoids the git-bash curl JSON-escaping 500; see SDS-47 pitfall), include `X-Paperclip-Run-Id`, then verify `status: done` + `completedAt` via fresh GET and the comment via the comments-list endpoint (newest-first — check index 0, see pitfall above).

## Procedure — capability question wake ("do you have the X skill?")

A user-created manual issue that ASKS whether the agent has a skill is an information
request, not a task. It does NOT take the `missing_skillset` path — that gate is only
for when an actual task REQUIRES the absent skill (intent gate step 3). Answer
honestly from the live `skills_list` and close done (verified SDS-74, SDS-75, 2026-09-01):

0. **Named-skill vs capability questions.** "Do you have the X skill?" (singing, SDS-74)
   → inventory the skills only. "Do you have the X capability?" (vision, SDS-75) → check
   the TOOLSET first (e.g. `vision_analyze` absent from the tool list, `read_file` cannot
   decode images), THEN the skill inventory — a capability may exist only as a tool with
   no skill named after it. Both are information requests: answer honestly, close done.
1. **If the named skill exists verbatim** — confirm it, one line on what it does, offer
   to apply it.
2. **If it does NOT exist** — say NO plainly. Do not claim an uninstalled skill or an
   absent tool, do not fabricate capabilities. Then list the ADJACENT installed skills
   that partially cover the ask, each with a one-line what-it-does (e.g. "singing" →
   `songwriting-and-ai-music` Suno prompts, `heartmula` song generation from lyrics+tags,
   `sound-production` audio engineering, `songsee` spectrogram analysis; conclusion:
   "can write songs / generate AI music, but no dedicated singing/vocal skill"; "vision"
   → no `vision_analyze` tool + `read_file` can't decode images; adjacent:
   `ocr-and-documents` text extraction, `viewport-screenshot-capture` capture-only,
   `segment-anything-model` segmentation masks, `ascii-art`/`ascii-video` display,
   `computer-use` requires the absent `computer_use` tool). This is the deliverable.
3. **Deliver** as ONE agent-type comment via minted key (POST 201) + bare
   `PATCH {"status":"done"}` (200) + key revoke (200 `{ok:true}`) — same single-process
   Python urllib sequence as any answer delivery (see Prerequisites). Verify
   `status: done` + `completedAt` + comment authorAgentId = you.
4. **No work product, no commits, no reference edits** — a pure Q&A needs none.
5. Post-wake knowledge-graph duty still applies: write the issue node with [[links]] and
   trigger the agent knowledge-graph refresh. Node convention (SDS-74.md / SDS-75.md):
   `SDS-<NN>.md` in the execution workspace — header `# SDS-NN — <title> (done)`, a
   Status / Type / Assignee block, `## Summary` with [[skills_list]] + sibling-issue
   links, `## Delivery` (mint→comment→PATCH→revoke rundown, no temp artifacts leaked),
   `## Links`. Refresh = POST
   `/api/agents/<id>/knowledge-graph/refresh?companyId=<cid>` → 200. **Fallback when the refresh route is absent (SDS-81, 2026-09-03: this server's `/api/openapi.json` listed no `/knowledge-graph/refresh` route — only external-objects refresh + liveness preview/run; **re-appeared by SDS-82, 2026-09-04**: `POST /api/agents/<id>/knowledge-graph/refresh?companyId=<cid>` returned 200 with the regenerated bundle — probe `openapi.json` or just try the POST first, use refresh when present, fall back to the PUT only when the route is genuinely absent):** patch the bundle file directly — `PUT /api/agents/<id>/instructions-bundle/file?path=KNOWLEDGE_GRAPH.md` with body **`{"path":"KNOWLEDGE_GRAPH.md","content":<full file>}`** — `path` is required in BOTH the query AND the body (a body with `content` only → 400 `Validation error ... path Required`); the PUT returns 200 `{path, size}`. **Fetching the current file also REQUIRES the query param — `GET /api/agents/<id>/instructions-bundle/file?path=KNOWLEDGE_GRAPH.md`** (without `?path=` → `{"error":"Query parameter 'path' is required"}`, observed SDS-82): read-then-append-then-PUT keeps past diary sections intact. Verified update shape: append an `## Issue nodes (akashic)` table (`id | file | status`) plus [[links]] edges (sibling issues, board-ops, the required skill). See `references/sds-81-bare-patch-bundle-put.md`.
   **Refresh output is BUNDLE-scoped, not workspace-scoped (observed SDS-78,
   2026-09-02):** the 200 response body's regenerated graph lists ONLY the
   instructions-bundle files (KNOWLEDGE_GRAPH.md, SOUL.template.md, TOOL.md) as nodes —
   the workspace `SDS-<NN>.md` files are on-disk records, never indexed graph nodes, and
   the "3 markdown files, N edges" line in the response reflects that. Do NOT expect the
   refresh to list your workspace node, and do NOT re-write `workspaces/*/KNOWLEDGE_GRAPH.md`
   (ignored by the UI). The graph presence for an issue comes from the bundle's own
   KNOWLEDGE_GRAPH.md; the workspace node file is the durable record + its [[links]].

## Procedure — base-capability request wake ("can you do X?" where X is a base capability)

When the wake is a creative/capability REQUEST carrying a concrete ask (SDS-83, 2026-09-04:
"can you do creative writing? like writing a screenplay?" for an astrological short reel),
triage by WHAT the task requires BEFORE any missing_skillset:

- **Skill-gated task** (factual/data/tool-dependent — e.g. SDS-82 "where is the sun?"
  needs ephemeris computation → `missing_skillset: astrology`): requires a specialized
  procedure/data source absent from the assigned skillset → the missing_skillset path.
- **Info-request about a skill/capability** (SDS-74/75: "do you have X?") → answer from
  skills_list/toolset, close done, no deliverable (procedure above).
- **Base-capability REQUEST** (SDS-83: creative writing / screenwriting): NOT skill-gated —
  writing/creativity is a core LLM capability, and astrology-theming is the Astrologer's
  identity. Answer YES honestly, then DELIVER in the same wake: write the artifact to the
  workspace, post the full text as the report comment (`POST /api/issues/{id}/comments`,
  plain `{body, authorType:"agent"}`), then bare `PATCH {"status":"done"}` — same
  delivery sequence as any answer; a minted agent key is only needed when agent-type
  authorship matters. **Re-wake variant (SDS-83, 2026-09-04):** if a later wake finds the
  issue `in_progress` with the deliverable comment already posted, do NOT re-post it —
  complete the deliverable's promised follow-up instead (e.g. compute the real sky event
  for the fill-in slot), post ONE follow-up comment with the computed/verified data, then
  bare-PATCH done. If the deliverable promised "real data on request", the re-wake is the
  moment to deliver it — never just flip the status while the placeholder stands.
  **Lock-wake variant (SDS-83 re-open, 2026-09-04 11:41 UTC):** when the re-opening comment
  is the USER echoing your own draft back ("if you hand me the @handle and VO gender, I'll
  finalize the title-card line"), it is a go-ahead to LOCK, not a stall — resolve the
  resolvable input by construction (VO gender → audit all VO lines; none gendered → adopt +
  document a gender-neutral series standard), isolate the un-inventable input (brand
  @handle → keep `@HANDLE` as a marked title-card macro, ask once, never fabricate),
  re-execute the ephemeris script to verify EVERY promised anchor, post ONE lock-status
  comment (✅ locked / ⏳ open macro), then bare-PATCH done. Pattern source:

## Procedure — productivity review wake (`issue_productivity_review`)

The watchdog fires on assigned issues showing stalled progression (`long_active_duration`,
`high_churn`, `no_comment_streak`, `resolved_review_snooze`). The wake issue's description
embeds the trigger evidence (sampled runs, cost, comments, thresholds) and the manager
decision options (close as productive / snooze / reroute / block / stop).

1. **Judge by the live board, not the evidence table.** `GET /api/issues/<source>/runs` +
   comments + cost. **Close as productive when every run died on infra before doing any
   work** — `Process lost -- server may have restarted` / `fetch failed` /
   `adapter_failed` — with 0 cost events, 0 assignee comments, no artifacts. The long
   "active episode" is a stranded-issue artifact, not churn (DCO-2 pattern). Observed
   SDS-52 (2026-08-13): 12h15m active, 3 runs, all infra-died.
2. **The system usually already moved the source to `blocked`** with a recovery owner +
   action id (system comment). The recovery owner records the manual resolution: fresh
   board sweep (state unchanged since last stand-down → nothing to originate), then close
   the source `done` via **bare PATCH (no comment)** — the original run failed, so a
   bundled comment would trigger the deferred_comment_wake reopen loop.
3. Record the verdict in the decision log (fresh-GET `baseRevisionId` first) and the
   board-state reference.
4. **Continuation echo — the review issue itself suffers the same infra storm.** Runs
   ladder: `issue_assigned` → `missing_issue_comment` → `issue_continuation_needed` →
   `source_scoped_recovery_action` → `retry_failed_run` → `issue_continuation_needed`,
   each carrying `retryOfRunId`. A zombie of a failed run can land ALL the writes
   (decision-log section, both status flips, disposition comment, reference update)
   while a later continuation run is still starting. If the wake arrives with the issue
   already `done` + disposition comment: identify yourself via
   `contextSnapshot.wakeReason`/`retryOfRunId`, verify the evidence chain landed
   (decision-log rev, reference section, both statuses `done`, `completedAt` set, no
   active/execution runs), and **stand down with ZERO writes** — no PATCH, no comment,
   no reference edit (the sibling already wrote it; racing corrupts shared state).
   `completedAt` refreshing mid-verify is a zombie-still-writing tell — re-verify after
   it settles, don't fight it. Re-observed on the DCO board (DCO-23, 2026-08-15): the
   wake comment IS the sibling's user-type disposition comment, and the sibling's
   agent-type verdict comment landed ~25s AFTER the echo run was created (12:48:55Z vs
   echo 12:48:32Z) — a `succeeded` closing run's session can still be writing during
   the echo. Do NOT treat early absence of the agent verdict comment as a gap; re-verify
   after it settles. DCO has no decision-log host (DCO-21 documents list empty) — the
   close-PATCH comment is the disposition record; don't hunt for a log (see
   paperclip-ceo `references/productivity-review-resolution.md`).
5. **`high_churn` with REAL work + external gate = productive too (DCO-23, 2026-08-15).** The
   trigger is not automatically noise: DCO-22 showed 11 runs/2 assignee comments in 1h — 7
   infra-failed (`adapter_failed` fetch failed / `process_lost` server restart), 2 succeeded
   with substance (blocked-diagnosis comment + final verified report), 0 cost events, and a
   genuine external gate (Atlas IP whitelist → operator whitelisted → re-probe found the
   dev-side dual-mongoose/collection-mismatch defect). Source issue was already `done` before
   the review concluded (completedAt refreshed mid-review by a sibling re-close). Two extra
   conventions learned: (a) a USER ask posted on the DONE source issue (e.g. "compose
   something real using the creative-writing skill") spawns its own sibling run that owns it —
   flag it in the review's disposition comment, do NOT act on it; (b) the DCO board has NO
   decision-log host (DCO-21 "Strategic Review" has zero documents — unlike XXX-12 / SDS-30),
   so the review close-PATCH comment IS the disposition record; no document append exists to
   make. Close verdict: single `PATCH {"status":"done","comment":...}` on the review issue —
   echo wake on the now-done review is expected and stands down.

### Ad-hoc verification for doc/plan deliverables (no test suite)

When the deliverable is a committed markdown plan (no canonical test/lint/build), verify with a throwaway script — create it under the OS temp dir via `tempfile.mkstemp(prefix="hermes-verify-", suffix=".py")`, run it, `os.unlink()` it after. **Simpler alternative that avoids the heredoc entirely (verified SDS-54, 2026-08-13): write the script directly with `write_file` to a fixed path under the OS temp dir (e.g. `C:/Users/pc/AppData/Local/Temp/hermes-verify-<topic>.py`), run it with `python <path>`, then `rm` it.** Sibling runs on the SAME issue can grab the same `hermes-verify-<topic>.py` temp path mid-session (write_file "modified by sibling subagent" warning on the throwaway path, observed SDS-56 2026-08-14) — the temp path is disposable, so overwrite-and-run is fine; only the workspace DELIVERABLE paths need re-read-before-write care. `write_file` does the escaping correctly and there is no bash heredoc → python string → tempfile layer to mangle anything — only use the mkstemp+heredoc route when the script must generate its own temp path at runtime. Authoring the script via a bash heredoc on Windows: keep the nested script **flush-left (column 0) inside the triple-quoted string with zero backslash escapes** — `textwrap.dedent` on indented content and `\\n`/`\\` escapes both get mangled through the heredoc → python string → tempfile layers (observed SDS-47, 3 failed attempts). Use forward-slash paths (`"D:/Dev/agent"`) and plain `print()` instead of `"\\n"` inside strings. **Bash `/tmp` is invisible to native Windows Python (MSYS path mapping, observed SDS-55 2026-08-14):** a file written by bash redirection (`python compute_chart.py ... > /tmp/sds55_natal.json`) cannot be opened by a later native `python -c` read — `FileNotFoundError: /tmp/sds55_natal.json`, because git-bash's `/tmp` maps to an MSYS-internal path that Windows Python doesn't resolve. For any file produced by one tool and consumed by the other (bash writes JSON → python reads it), use a Windows-visible path on BOTH sides (`C:/Users/<user>/AppData/Local/Temp/...`) — never `/tmp` for cross-shell intermediates. **Assign repeated `find()`/`index()` results to local variables before the `check()` line** — long boolean chains (`ref.find("...") >= 0 and ref.find("...") > ref.find("...")`) inside a single `check(...)` call trip paren-counting SyntaxErrors (`unmatched ')'`) that are near-impossible to spot through the heredoc → string → tempfile layers (observed SDS-52, 2026-08-13: one-line check failed, fixed with `i50r = ref.find("...")` / `i52r = ref.find("...")` first, then `check(..., i50r >= 0 and i52r > i50r)`). Check four layers:

1. **Content contract** — file exists; every required section heading present (regex per `## N.` heading); every spec-mandated content bit present (issue description → exact substrings).
2. **Git state** — file tracked (`git ls-files --error-unmatch`); last commit for the file is the expected SHA (`git log -1 --format=%h %s -- <file>`); `git show --stat <sha>` touches exactly that file; `git diff HEAD -- <file>` is empty (race-safe). **Do NOT md5-compare `git show HEAD:<file>` against the working tree on Windows — CRLF checkout makes the hashes differ even when content is identical** (observed SDS-55, 2026-08-14: 374ebfea vs 736d75d4 for the same doc). If you must hash-compare, normalize both sides first (`git show HEAD:<f> | tr -d '\r' | md5sum` vs `tr -d '\r' < f | md5sum`), or just trust the empty `git diff HEAD` check instead.
3. **Board outcome** — issue `done`, no active `executionRunId`. For a gate that must NOT close yet (waiting on a real external event), assert the negative instead: `status != "done"` + `completedAt` null — proving you didn't fabricate closure (SDS-44 pattern).
4. **Pitfall:** don't string-match the commit *message* for the filename — messages are title-case (`docs: define X team structure and goal milestones (SDS-34)`), not the snake-case path. Assert via `git ls-files` + `git show --stat` instead.
5. **A FAIL in your own assertion is a script bug, not automatically a defect in the change** (observed SDS-49, 2026-08-12): a "no temp artifacts" grep for `hermes-verify-` false-positives against the board-state reference because its SDS-46 section documents that naming convention. Re-read what the target file legitimately contains and fix the assertion before re-running. The verification harness may also re-request evidence after a clean ad-hoc run (evidence is turn-scoped) — re-run the same script and re-report; treat the re-request as a re-check, not a failure signal.
5. **Shared reference files (board-state, decision-log mirrors): skip the "my section is last" assertion.** Sibling wakes append to the same reference mid-run, so the tail is not stable — asserting your section is the LAST `## Update` fails minutes after you write it (observed SDS-44/SDS-48, 2026-08-12: the SDS-48 section landed after mine while my script was running, failing the check despite a correct change). Assert instead: your section is present, prior sections are intact and ordered before yours, and ANY later sections do not contradict your recorded facts (same status claims, same commit hashes, same gate verdict). Report the sibling append explicitly rather than "suite green".
6. **Markdown substring assertions must whitespace-normalize the target (`" ".join(doc.split())`) and match the artifact's OWN figure format** (observed SDS-57 follow-up, 2026-08-16: 17 FAILs, all script bugs). (a) Line wraps split phrases across newlines — "both in the 5th" / "in the 11th" read as `both in the\n5th` in the raw file, so raw-substring matching FAILs on correct content; normalize before matching. (b) Derive expected position strings in the RECORD's convention (`Sun 29 Cancer 12`, degree-before-sign) — my first formatter emitted `Sun Cancer 29 12` and failed against a correct doc. (c) Don't assert a commit hash inside the doc text when it legitimately lives only in the board comment/reference — provenance is covered by `git log -1 --format=%h -- <file>`. (d) Bonus contract worth asserting for chart-derived docs: Rx markers present near retrograde planets (~60 chars) and absent near direct ones (~25 chars).

If the board check flaps mid-run (see wake-loop pitfall), the artifact checks are still meaningful — re-run after the queue settles and report the flap explicitly rather than claiming suite green.
