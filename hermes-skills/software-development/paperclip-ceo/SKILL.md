## Core Workflow

The orchestration loop operates in six phases:

### 1. State Acquisition
- Review goals, projects, open/blocked issues, and inbox
- Assess current capacity and idle teams
- Identify execution gaps

### 2. Gap Detection
- **Decompose the goal into its constituent motions — check EACH has an owner.** The AppZeno goal is "land AND deliver client web/mobile projects profitably": a two-motion goal. A review that only checks "is there work?" misses a whole half. 2026-08-11 XXX-16: the entire upstream funnel (offering XXX-79, one-pager XXX-74, pitch XXX-76, blog XXX-63) was owned and executing — but NOTHING owned the "land" motion (prospect identification, outreach, first-client conversion). Originated XXX-87 (high, Growth Marketer, blocker XXX-79) precisely because acquisition was the unowned half. For any goal with an "A and B" shape, enumerate the motions and verify each has an issue + assignee; the empty half is the highest-value originate.
- Board intents with no assigned owner
- Blocked work requiring an owner
- Goal milestones with no execution plan
- Idle teams with available capacity
- **Unanswered user asks on concierge issues** — check the Board Operations issue (and any `todo` standing/concierge issue) for user comments with no agent response on record. These are first-class unowned work even when no issue was ever created for them; originate a properly-scoped issue (assignee + goal + project) rather than answering inline. (Verified 2026-08-11, XXX-72: an 11-hour-old pitch request on XXX-12 became XXX-76, assigned to the idle Growth Marketer.)
- **`in_review` deliverables with no active run are unowned CEO review work — and their artifacts carry first-class gap markers.** During the state scan, check every `in_review` issue for liveness: `active-run` null + no heartbeat entry carrying its UUID = nobody owns the review step, and the CEO owns it. Verify the deliverable on disk (exists, non-empty, required sections) and scan the ARTIFACT (not just the issue trail) for embedded gap markers — `REVIEW NOTE` / `TODO` / `TBD` / "contact channel TBD" — the originating issue may be complete on its own terms while its artifact explicitly flags unowned follow-up work no issue tracks; that flag is a first-class gap. Close the deliverable `done` with a review disposition (or send back with specifics) AND originate a properly-scoped follow-up (assignee + project + goal, description quoting the artifact's own text) rather than closing with the gap unresolved. (2026-08-11 XXX-74: one-pager verified 106 lines / 5588 bytes, approved done, follow-up XXX-84 created for the TBD intake channel; sibling pass on XXX-75 originated XXX-80 — "Define client intake channel and acquisition landing presence", high, Growth Marketer, goal + project wired — for the same REVIEW NOTE.)

- **Decision-log deferred items convert to gaps the moment their stated prerequisite lands.** The log often parks CEO items behind an explicit precondition ("define goal milestones after capability plan — deferred since XXX-72"). Each review, re-check parked items against the issues list: when the prerequisite issue flips to `done`, the parked item is no longer deferred — it is a first-class gap. Verify concretely, don't trust the log alone: `GET /api/goals/{id}` → `milestones: null` is the gap signal for milestone work; `ownerAgentId` confirms who should own it. Then originate a scoped issue wired to the goal. (Verified 2026-08-11 XXX-86: goal milestones deferred in XXX-72 and XXX-17 pending XXX-79; XXX-79 landed done → originated XXX-88 "Define AppZeno goal milestones" high/CEO/goal-wired in the same review.) In a full-pipeline review this is often the ONE legitimate origination — everything else has a live run.
- **Greenfield / company-inception boards** (wake on a non-AppZeno company, no org yet) and **multi-issue origination identifier staleness** (descriptions referencing sibling issues by pre-creation identifier go stale): full playbook in `references/greenfield-inception-review.md`.

### 3. Initiative Creation
- Create issues with appropriate assignment
- Set priority levels
- Wire first-class blockers via `blockedByIssueIds`

### 4. Executive Delegation
- Assign work to team leads or specialized agents
- Maintain oversight through child issues
- Monitor execution progress

### 5. Board Reporting
- Update Board Operations decision log
- **DCO-18 Enhancement:** Verify issue files have proper structure
- Document key decisions and actions

### 6. Strategic Closure
- Mark issue complete with clear next actions
- Close only when durable trail exists
- Explicitly state when no action needed

### Board State Acquisition (REST — verified)

The board state lives in the Paperclip REST API, not in repo files. Query it directly:

- **Discovery when `PAPERCLIP_*` env vars are NOT injected** (manual session, local dev): read `~/.paperclip/context.json` — it holds `profiles.<currentProfile>.apiBase` and `.companyId`. In `local_trusted` mode no auth header is needed for local requests.
- **The local server hosts MULTIPLE companies — resolve yours by issue prefix, never trust context.json's companyId alone.** A wake's task context names the issue key (e.g. SDS-29); the prefix identifies the company: AppZeno = XXX (91fab276-9efc-4f5e-b7dd-5db1d5e2d03a), Astrologics = SDS (d1551a02-e62d-4a5b-aeb7-c2eadf686aa0), ApniDesi Dukaan = DCO (9b4623fa-47b9-4f24-9f57-c6fc402fbde8). `~/.paperclip/context.json` defaults to the AppZeno company (verified 2026-08-12 SDS-29). Always `GET /api/companies`, match `issuePrefix`, then use that company's UUID for goals/projects/agents/issues/heartbeat-runs, and locate its Board Operations decision-log host within the resolved company.
- Issues: `GET /api/companies/{CID}/issues?limit=200` (each item includes `blockedBy`/`blocks` arrays with identifier+status)
- Comments: `GET /api/issues/{id}/comments` (system recovery comments included — key for duplicate detection; route is FLAT like issue detail — the company-prefixed `/api/companies/{CID}/issues/{uuid}/comments` returns `{"error":"API route not found"}`, verified 2026-08-11 XXX-63). **Newest-first ordering** — `comments[0]` is the latest, `comments[-1]` the oldest (re-verified 2026-08-11 on XXX-77/XXX-76/XXX-12 fetches). (2026-08-11 XXX-31: tail-indexing grabbed the 08:11 auto-retry comment instead of the just-posted one; verify a posted comment by count increase + returned id, not by list tail)
- Run liveness: `GET /api/companies/{CID}/heartbeat-runs?limit=15` — check status/error BEFORE any disposition; `fetch failed` / `Process lost -- server may have restarted` = infrastructure, not productivity. Each run's `contextSnapshot` holds the issue UUID it wakes on — build an id→identifier map from the issues list and cross-reference to see exactly which issues have queued/running wakes (and when each was enqueued).
- Goals: `GET|PATCH /api/goals/{id}` (e.g. `ownerAgentId` to claim the goal)
- Routines: `GET /api/routines/{id}` — cadence cron, `status` (paused/active), `concurrencyPolicy` (`skip_if_active` = self-limiting while a live issue exists; check this before deciding the routine will keep spawning), trigger `lastResult`
- Agent/adapter shapes: `GET /api/companies/{CID}/agent-configurations` (hermes_http uses `{command, instructionsFilePath}` + `paperclipSkillSync.desiredSkills`)
- Hire: `POST /api/companies/{CID}/agent-hires` → activate `POST /api/agents/{id}/approve` (`pending_approval` → `idle`). Response is NESTED `{agent, approval}` — read `resp["agent"]["id"]`. `desiredSkills` top-level only (server writes `paperclipSkillSync`). Recipe: `references/hire-agent-flow.md`
- Documents: `GET|PUT /api/issues/{id}/documents[/decision-log]` — the decision log is a document on the Board Operations issue. **PUT requires `baseRevisionId`** (GET the doc first, take `latestRevisionId`, include it — otherwise 409 Conflict) **plus `format: "markdown"`** (missing `format` 400s — verified 2026-08-12 SDS-30) and **replaces the whole body** (append your new section to the existing log content; sending only the new entry clobbers the prior history). **READING content — the LIST route is the only working read path:** `GET /api/issues/{id}/documents` embeds each document's full markdown `body` inline (plus `key`, `title`, `format`, `issueId`), so to verify a claimed decision-log entry just GET the list and grep `body` for the issue key. The per-document fetch routes DO NOT exist: `GET /api/documents/{docId}` → `{"error": "API route not found"}` and `GET /api/issues/{id}/documents/{docId}` → `{"error":"Document not found"}` (verified 2026-08-11 XXX-79 — don't probe them, go straight to the list route).

## Pitfalls to Avoid

- Never close without a clear next action
- Don't confuse infrastructure failures with productivity issues (e.g., DCO-2 pattern where runs fail with `liveness: failed` but no comments, indicating infrastructure not productivity).
- Always record disposition comments
- Verify run liveness before assuming productivity problems
- **Stale duplicate piles from cadence routines.** A routine that fires on a short cron (e.g. `*/5 * * * *`) creates a new issue per fire; when runs fail at the adapter/process level (`fetch failed`, `Process lost`), each failure auto-blocks the issue and the next fire spawns another. Symptom: dozens of same-titled blocked issues (e.g. all "Strategic Review"), all `blockedBy: []`, all carrying the identical auto-generated "Paperclip automatically retried continuation … Moving it to blocked" sys comment. Treat the pile as board hygiene: cancel the stale duplicates with a disposition comment, keep the current cadence issue, and close the superseded original. Do NOT resume the paused routine blindly — check its `lastResult` first ("Skipped because a live execution issue already exists" means the cadence is already self-limiting). Resuming IS the right call once the infra is stable again: 2026-08-11 XXX-72 resumed paused→active with 200 OK after the 16:13 `process_lost` cleared — criteria: recent heartbeat-runs all succeeded (no `fetch failed` / `process_lost` since the last failure), the pile members carry their own live wakes (so they self-drain), and `concurrencyPolicy: skip_if_active` prevents a fresh spawn while any live execution issue exists. A paused cadence means the company goes dark after the current batch drains; the goal text ("keeps moving toward its goals even when no one hands you work") is the mandate to resume. **Routines API field gotcha (2026-08-11):** `GET /api/companies/{CID}/routines` list items expose the title as `title`, NOT `name` (filtering on `r.get('name')` silently returns None); the detail endpoint `GET /api/routines/{id}` returns `lastResult: null` / `lastFiredAt: null` / `cron: null` for an ACTIVE routine — null lastResult does NOT mean the cadence is dead. Verify liveness via `GET /api/companies/{CID}/heartbeat-runs` (status `succeeded`/`failed`/`queued` + error text) instead of trusting lastResult alone.
  - **Short routine IDs from wake comments don't resolve — and comment claims about routine state can be stale.** `GET /api/routines/<8-char-prefix>` (e.g. `30b21fd4`) returns an all-null object *including `id: null`* — resolve the full UUID from `GET /api/companies/{CID}/routines` (match by `title`) before reading status. A wake comment saying "routine paused, no new spawns" may already be false: XXX-52 (2026-08-11) claimed paused, actual list state was `active` + `concurrencyPolicy: skip_if_active`, which self-limits while any `in_progress` cadence issue is live (XXX-75 had its own running wake) — so no spawn loop, but verify against the list rather than the comment.
- **Windows / git-bash: `curl -o /tmp/…` then Windows-python read fails.** Git-bash's `/tmp` maps to a path the native Windows Python can't see (`FileNotFoundError: /tmp/issues.json`). Write API dumps to a relative local file (`curl -s … -o issues_dump.json`) or pipe curl straight into `python -c` — never round-trip through `/tmp`. **Two more Windows-box quirks (2026-08-11):** (a) `curl http://localhost:3100` fails with exit 7 (IPv6 resolution) even though `~/.paperclip/context.json` stores `localhost` as apiBase — use `http://127.0.0.1:3100` for every request; (b) dump files written in one terminal call can be GONE by the next call (issues_dump.json / heartbeat_dump.json parsed fine in-call, then FileNotFoundError next call; cause unconfirmed — possibly sandbox or parallel-process cleanup) — chain fetch + parse + cleanup (`curl … -o x.json && python -c … && rm -f x.json`) in a SINGLE call, or pipe curl straight into python. **Prefer the `-o <relative-file>` form over piping:** the pipe can intermittently deliver an empty body even on HTTP 200 (observed 2026-08-11 on issue-detail GETs — two consecutive `json.load` failures on empty stdin, same URL fine via `-o`). If `json.load` hits empty input, retry with `-o` and read the file. **Same class of miss in `execute_code`:** its scripts run from a temp sandbox dir (`C:\Users\…\Temp\hermes_sandbox_*\script.py`), so relative paths inside the script do NOT resolve to the session cwd — open dumps with absolute paths (`D:\Dev\agent\issues_dump.json`) or the sandbox raises `FileNotFoundError`. And since dumps land in the repo cwd, `rm -f issues_dump.json heartbeat_dump.json …` after parsing to keep the tree clean.
- **Re-verify artifacts at disposition time.** An earlier "Confirmed file exists" comment can be stale (workspace resets, file deleted). Before marking an artifact issue done, re-check the file/workspace actually contains the deliverable; if gone, note it and set the correct disposition.
- **Parallel CEO wakes converge on the same artifacts — verify the CONTRACT, not your write receipt.** With maxConcurrentRuns > 1, several Strategic Review wakes execute simultaneously and can both "restore" the same deliverable (2026-08-11 XXX-72: two wakes re-created test.md for XXX-8; a sibling's richer 21-line/513-byte version superseded my 6-line/210-byte write BETWEEN verification runs). A verification script that asserts your exact byte/line count goes red against a legitimately better sibling version — that is a stale assertion, not a broken deliverable. Assert the deliverable contract instead (file exists, non-empty, expected header, key referenced strings) and note the sibling enrichment in the audit comment. Same rule for the decision log: re-`GET` the document before PUT; if a parallel wake already wrote the section for your issue, skip the full write and append only a short addendum covering what the sibling missed (e.g. an issue you originated that it never saw).
- **Wake comments are self-reports — verify before accepting "Done".** When waking to a task whose wake comment claims a deliverable (doc written, endpoint added, file created), independently confirm the claims against the actual code before closing: file exists with claimed size/line count, every port/endpoint/claim traces to a real `file:line` (grep the source), referenced docs exist. For repo-artifact tasks, also check **git state**: `git log --oneline -1 -- <file>` + `git status --short <file>` — a committed deliverable (visible in history, no pending diff) is stronger proof than a working-tree file that could be a dangling edit from a crashed run. **Line/byte-count claims verify against the EXACT cited commit, not the working tree:** `git show <commit>:<file> | wc -lc` — a disposition claiming "195 lines / 11,091 bytes" can match its cited commit (`f83e07af`) byte-for-byte while HEAD and the working tree differ (later cleanup commits + uncommitted edits, 2026-08-11 XXX-78/79 verification). Report the delta as expected drift, not a false claim. Then post an audit comment on the issue citing the `file:line` evidence — the trail should show independent confirmation, not just the reporter's word. This session's README-verification pass (ports, `/chat/sync`, `/events/ws`, `/api/v1/live`, presence POST) is the template; the pre-built evidence map for the AppZeno repo lives in `references/appzeno-repo-verification-map.md` (incl. the gotcha that board-UI code like `LiveUpdatesProvider.tsx` lives under `paperclip/ui/src/`, not `Mithuna/`).
- **A `done` issue with a "succeeded" run can still be undelivered — and the runs feed won't tell you.** `GET /api/issues/{id}/runs` returns run summaries (runId/status/agentId/timestamps) but `stdoutExcerpt`, `logRef`, `error`, `exitCode` all come back null for hermes_http runs — you cannot recover what a run produced from the API. Judge delivery by the trail (comments on the issue AND on the standing concierge issue) and repo artifacts only. When a task is a re-ask (CEO re-originated because "no response has been posted"), check the PREDECESSOR issue's comments/artifacts to confirm nothing was ever posted, and state that in your disposition (2026-08-11 XXX-77: XXX-76 was marked done by the Growth Marketer with a succeeded run but zero comments anywhere — the pitch was never delivered; XXX-77 was the real delivery).
- **"Verified, closing" ≠ closed.** A wake comment ending "Verified, closing" only means the previous run *intended* to close — it may have commented without PATCHing status (XXX-61: left `in_progress`). Verify `GET /api/issues/<uuid>`: if not `done`, close with the single-call `PATCH {"status":"done","comment":...}` and confirm `completedAt` set. **Mirror — already `done`:** with a prior audit trail, do NOT re-PATCH (churns `updatedAt`, re-triggers watchdogs); post the audit comment only when you carry a genuine delta (fresh probe, uncited SHAs, log not naming closure), skip when trail + log carry everything (XXX-8).
- **The `done`→`todo` wake-delivery flip is the mirror of the cancelled flip — restore `done` (+`assigneeAgentId:null`) the same anti-resurrection way, but ONLY as the sole run.** XXX-38: audit comment posted on a snapshot that had already flipped (completedAt cleared) — "already done = verify and stop" applies while status is still `done`; once delivery flips it to `todo` mid-verification, restore with ONE `PATCH {"status":"done","assigneeAgentId":null,"comment":...}` so the machinery stops re-delivering the closed cadence issue. Preconditions: active-run null, only your own wake entry on the UUID, no queued run. Confirm on follow-up GET (done, completedAt re-stamped, assignee None).
- **Verification-pass audit comments carry observations forward for the live sibling run — don't act on them yourself.** When the wake lands on a completed cadence issue and a NEWER cadence issue (e.g. XXX-86) is already `in_progress` with its own running wake, that sibling owns the current review, new-work origination, and decision-log writes. The verification pass lists its findings in the audit comment for the sibling to pick up (2026-08-11 XXX-38: flagged near-duplicate XXX-84/85 intake-channel issues both in_progress on CMO with live runs, XXX-77 flipped back to `todo`, XXX-63 re-opened at 16:56Z — all left to XXX-86's run rather than re-assigned/closed by the pass). Same principle as the reassignment race: reconcile via comment, don't fight. **Even `done` issues can flip to `todo` mid-verification (2026-08-11 XXX-73):** the flip is not always caused by your own comment — it can be the wake delivery for SIBLING runs (here: `issue_blockers_resolved` / `issue_commented` wakes spawned when the parent XXX-63 closed), landing minutes after your freeze check and predating your audit comment. When the post-comment re-GET shows `todo` and heartbeat-runs shows any live (running/queued) run on the UUID, that run owns the disposition — stand down completely: no re-PATCH, no further comments (your verification comment spawned no new run, `wakeCommentId` check confirmed; the pre-existing siblings were the flippers). The sibling runs will re-verify/re-close; racing them just churns the board. Full marketing-wake recipe (CMO identity, brand-voice pass, done-issue verification): `references/marketing-role-wake.md`. **Trail-saturated variant (2026-08-11 XXX-8):** when the wake comment ITSELF is the disposition, an independent verification comment for the same deliverable is ALREADY on the issue trail, and the decision log already names the closure — skip the extra verification comment too; posting another is board churn (the anti-churn convention the decision log itself documents: "no re-fought", "no PATCH ping-pong"). Re-verify the deliverable on disk (size/line count/contract elements) and the issue status with fresh GETs — `completedAt` can be re-stamped by parallel wakes re-confirming, and a sibling's later fetch may show a newer close time than your first read — then carry the verification in your wake report instead of writing to the board.
- **A comment POST reopens a `done` issue — even a FAILED one; never separate the disposition comment from the status PATCH.** Restoring with a bare `PATCH {"status":"done"}` and then POSTing the disposition as a separate comment is a self-inflicted flip: the comment endpoint auto-reopens done issues (`GET /api/issues/{id}/activity` shows `issue.updated {source:"comment", reopened:true, reopenedFrom:"done"}`) — and the reopen fires BEFORE comment validation, so a POST rejected 400 STILL reopens the issue. Two 400 shapes seen on XXX-63 (2026-08-11): `authorType:"agent"` → "Comment authorType must match authenticated actor" (via the local API the authenticated actor is `user` — omit `authorType` or set `"user"`; `"agent"`/`"system"` are rejected), and `metadata` without the required `sections` array (`{version:1}` alone → invalid_type). My restore (PATCH → done, held 17:01:53Z) was undone at 17:02:38Z by my own rejected comment attempts; a sibling CMO wake on XXX-73 re-restored it at 17:04:33Z (final: done, completedAt 17:04:29Z). Rules: (1) close/restore with the single-call `PATCH {"status":"done","comment":"<disposition>"}` — the comment rides the PATCH and cannot reopen; (2) after a restore holds, verify with GETs ONLY — no further comment POSTs, even "verification" ones, on a done issue; (3) attribute flips with the activity feed — `issue.updated` details carry `_previous`, `reopened`, `reopenedFrom`, `source`, which distinguishes a self-inflicted comment reopen from genuine wake delivery; (4) if using `metadata` on a comment, it requires `sections` (array of typed rows: `text`/`code`/`key_value`/`issue_link`/`agent_link`).
- **The wake-delivery flip hits `done` issues too — "already done, don't re-PATCH" is a decision-time rule, not a first-GET rule.** XXX-63: issue verified `done`; re-GET after the verification comment showed the flip mid-audit (`todo`, completedAt cleared). Re-check status at DECISION time; if flipped, verify sole run (no queued/running run on the UUID in heartbeat-runs; `activeRun: null` NOT proof; `updatedAt` frozen ~5s apart; re-check after ~30s for queued-run lag), restore with ONE `PATCH {"status":"done","comment":"<disposition>"}`, confirm `completedAt` re-stamped in response AND follow-up GET. Full procedure + timelines: `references/verification-pass-and-flip-restore.md`.
- **Verification-pass discriminator: post vs. skip the audit comment — test = does an independent verification of THIS state already exist on the trail?** Prior-state verifications (written while `cancelled`) do NOT count — a `done` deliverable with zero same-state verification gets a fresh audit comment even when the wake comment IS the disposition (XXX-17); the XXX-8 skip applies only when a comment verifying THIS state already exists.
- **Trailing wake on a DONE cadence issue during a wake storm = verification pass; the delivered wake comment is NOT your assignment.** Resolve your actual wake: `echo $PAPERCLIP_RUN_ID` → find it in heartbeat-runs `contextSnapshot.issueId` (run id field is `id`, not `runId`; `contextSnapshot` may be a string — guard `isinstance(cs, dict)`). If your issue is already `done` with a saturated trail and a NEWER cadence issue's run is live, post ONE audit comment via the atomic `PATCH {"status":"done","comment":...}` carrying only the genuine delta (e.g. a sibling deliverable's DONE state no trail verified), flag the next unowned motion for the live sibling, originate nothing, skip the decision log. Confirmed 2026-08-12 (SDS-37): the PATCH-comment re-stamps `completedAt` but may spawn a verification run on the same UUID ~20-30s later (SDS-45: 3f6e70df; issue stays done); a bare comment POST reopens + spawns one. Full recipe: `references/trailing-wake-verification-pass.md`.
- **A verification pass does NOT resume a paused routine.** Done-issue wake + agents `paused` + routine `paused`: defer resume to operator/next FULL review (XXX-17). `paused` agents ≠ dark board — judge by heartbeat feed, not agents list.
- **A wake on a completed cadence issue can be a pure verification pass — and the heartbeat feed will LIE about run liveness.** When the wake comment IS the prior run's completion comment and the issue is `done` with `completedAt` set, check whether a NEWER cadence issue is already live (2026-08-11 XXX-26: successor XXX-86 `in_progress` with its own wake). If so, this wake is a verification pass, not a fresh review: verify the prior review's claims (closed issues, originated issues, decision-log section present), post the audit comment, and do NOT originate new work or append a decision-log section — the issue comment is the durable trail and the successor owns the next review. **Feed-status gotcha:** run entries in `heartbeat-runs` transition to status `cancelled` once their wake terminates — my own live wake (active-run `running` at 16:59, the same run) showed `cancelled` in the feed by 17:00. Never read feed `cancelled` as an aborted/failed/competing run; judge liveness by issue `updatedAt` + `active-run`, never by feed status alone. **Timing tell for the flip:** if the issue's `updatedAt` predates your comment's `createdAt`, the wake-delivery flip landed BEFORE you posted — you commented on an already-flipped snapshot. Doesn't change the playbook: sole-run check (no queued/running run on the UUID, updatedAt frozen, active-run null, your comment spawned no run), then ONE PATCH `{"status":"done","comment":...}` restores and holds (XXX-26: flip 17:00:05Z, comment 17:00:23Z, restore 17:01:23Z held on follow-up GET).

- **Issue-list parsing: the field is `identifier` ("XXX-78"), not `key`.** `GET /api/companies/{CID}/issues` items have no `key` field — printing `key` yields None for every row. Parse `identifier` + `assigneeAgentId` from the raw objects (the list returns full issue objects; build the keyed map with `{i.get("identifier"): i}`).
- **A `done` cadence issue can flip back to `todo` on a verification wake — restore to `done`, NOT `cancelled`.** The wake-delivery flip is not cancelled-only. A cadence issue closed by a parallel run spawns a verification wake within seconds of the close (`issue_commented`, wakeComment = the closing comment — XXX-19: close 16:54:48Z, disposition 16:55:08Z, wake 16:55:12Z). That signature (wake time ≈ disposition time) means verification pass, not new review — check the last comment's timestamp against your wake time before re-reviewing. But wake delivery can flip the `done` issue to `todo` (completedAt cleared) while you verify, and the flip can land BETWEEN your clean pre-comment GET and your comment (XXX-19: pre-GET showed `done`, flip 16:57:23Z, comment 16:57:37Z). Your comment then spawns a re-delivery run (`issue_reopened_via_comment`, wakeComment = your comment id) which does NOT own the disposition. Restore with ONE PATCH `{"status":"done","comment":...}` — the operator disposition for a completed review is `done`, and the restore held (XXX-19: completedAt 16:58:32Z set, status still `done` on follow-up GET; small updatedAt tick after restore is normal bookkeeping). Note `active-run` on a just-closed issue can return the CLOSING run (started pre-close) rather than the newest re-delivery run — it is the sibling that closed the issue, not a competing instance; judge by status + completedAt + heartbeat wakeComment correlation, never by active-run freshness alone.
- **`python -c` f-strings do NOT see bash vars, and a `;`-chained `rm` deletes your evidence on parse failure.** Inside `python -c "..."`, `f'{name}_{TS}.json'` interpolates `{TS}` at PYTHON level → `NameError: name 'TS' is not defined`; pass values via `os.environ` (export first) or hardcode the suffix in the filename. And never chain cleanup with `;` — if the parse fails, `rm -f *_$TS.json` still runs and deletes the dumps you need. Chain the `rm` with `&&` after a successful parse, or clean up in a separate call (2026-08-11 XXX-38: parse NameError → rm deleted the freshly-fetched goals/issues dumps → full re-fetch). Related: exported vars don't reliably survive between terminal calls (TS came back as a parent-shell `$$` value on the next call) — hardcode the timestamp suffix rather than trusting `export`/`$$` persistence.
- **Side items picked up mid-review can be closed by a sibling before you act — verify, then note in your report instead of touching.** An issue you spot during state acquisition (e.g. an artifact task assigned to you) may flip to `done` with its own running verification run while you are still reviewing (2026-08-11 XXX-8: `in_progress` at dump time, closed done 16:53Z by a parallel wake). Guard any close-PATCH with a fresh `GET` + `active-run` check and a conditional PATCH (status still open AND active-run null). If it is already `done`, do NOT re-PATCH and do NOT post a comment on it (the comment spawns a run racing the sibling's in-flight verification) — carry the independent on-disk verification (size + element counts) in your own wake's report instead. Generalizes to the whole cycle: a full pipeline with a live run per gap is a valid "originate nothing, verify + document" review — say so explicitly in the close comment rather than forcing new issues.
- **Wake on a stale duplicate AFTER the live cadence issue already completed the review — verify the sibling's trail, sweep the blocked pile, append only a delta.** (2026-08-11 XXX-25): the wake delivered on a `blocked` Strategic Review duplicate while the CURRENT cadence execution (XXX-86, higher identifier, flipped `in_progress`→`done` minutes earlier) had already run the full loop: review comment on its own trail, decision-log section written, next action originated (XXX-88, high/CEO/goal-wired). Do NOT re-execute the loop — re-reviewing duplicates the sibling's originated work and churns the board. Instead: (1) confirm the live issue's close comment + decision-log section actually cover state/gaps/next-actions; (2) sweep the REMAINING blocked pile — all members share the dead-duplicate signature (status `blocked` with `blockedBy` empty, active-run null, auto-retry sys comment "still has no live execution path", still assigned) — with ONE cancel+unassign PATCH per member, guarding each (re-GET: status still `blocked` AND active-run null) and verifying each (`cancelledAt` set + `assignee` null on follow-up GET; a 6/6 sweep held clean); (3) append only a delta section to the decision log (marker-check the body first to skip if a sibling already wrote it; GET → `baseRevisionId` → PUT; on 409 re-GET and retry); (4) close the wake issue `cancelled` with a disposition naming the live issue as the carrier of the review. Mechanism note: prior hygiene passes had cancelled these members but NEVER unassigned — the lingering assignee is precisely why recovery kept re-delivering them; cancel+unassign is the durable fix that makes the pile stay dead.
- **Watchdog `no_comment_streak` on a pile member = noise close, not productivity work.** (2026-08-11 XXX-90/91): "Review productivity for XXX-N" watchdogs spawned as the follow-on wave from the just-done SR pile triggered on `no_comment_streak` (11 consecutive completed runs with no run-created comment). Before treating one as work, read the evidence block in the description: 0 cost events + every sampled run `failed`/`cancelled` on infrastructure (fetch failed / process lost / agent pause pile churn) + source issue already `done` with a full audit trail ⇒ the streak is pile churn, not a productivity problem. Close `done` with a "productive/noise" disposition. Unassigned watchdogs need no unassign; guard status still `todo` + assignee null before the PATCH, then verify `completedAt` is set.
